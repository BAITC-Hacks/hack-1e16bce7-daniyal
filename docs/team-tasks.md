# Career Quest — распределение задач команды

## Цель проекта и текущий статус

Создать веб-приложение, которое показывает сотруднику профиль и карьерную
траекторию, определяет skill gaps до следующего грейда, рекомендует 1–3 активности,
объясняет выбор и обновляет навыки после завершения. HR получает аналитику
по сотрудникам, навыкам и активностям.

Сотрудник и HR работают в одном адаптивном Next.js-приложении: экран сотрудника —
`/`, HR — `/hr`. Отдельный native-клиент не входит в текущую архитектуру.

**Уже реализовано:** каркас Next.js/FastAPI/PostgreSQL, SQLAlchemy и конфигурация
Alembic, системные проверки API/БД, доменные модели, расчёт роста навыков и порты
ранжирования/объяснений. Есть пробное задание с localStorage; оно не обновляет
серверный профиль и не является оценкой сотрудника.

**Обновление AI:** engine и адаптер объяснений реализованы автономно. Точный контракт,
формула v1, запуск и границы ответственности описаны в [ai-integration.md](ai-integration.md).
Ниже сохранено распределение задач команды. JWT, бизнес-таблицы,
импорт в БД и подключение AI к HTTP API ещё предстоит реализовать. Числа, названия файлов,
поля и веса в примерах иллюстративны; окончательные правила согласуем по ТЗ и датасету.
Документ дополняет [архитектуру](architecture.md) и [этапы](roadmap.md).

## 1. Frontend Developer

### Стек и ответственность

Next.js, TypeScript, Tailwind CSS. shadcn/ui и Recharts — планируемые библиотеки,
пока не установлены. Frontend отображает полученные от API расчёты: отдельные
формулы scoring, readiness и роста навыков в браузере не реализуются.

### 1.1. Employee Dashboard

Показать имя, если оно есть в данных, или employee ID; роль, текущий и целевой грейд,
стаж, readiness до следующего грейда, основные gaps и следующую рекомендацию.

```text
Backend Engineer · Middle → Senior
Career readiness: 68% (пример)

System Design    2 / 4
Python           3 / 4
Communication    3 / 3
```

### 1.2. Career Path

Показать карьерную траекторию и требования следующего грейда из API.
Последовательность грейдов не хардкодить: она может зависеть от роли.

```text
Junior → Middle (Current) → Senior → Lead

Python             4 / 4 ✓
System Design      2 / 4
Leadership         2 / 3
Communication      3 / 3 ✓
```

### 1.3. Recommendations

Карточка показывает название активности, приоритет, затрагиваемые навыки,
текущий и требуемый уровни, gain, ожидаемый уровень, объяснение и изменение readiness.
Выбор и порядок определяет Python engine; AI формулирует объяснение готового выбора.

```text
System Design Workshop
Current: 2 / 5 · Target for Senior: 4 / 5 · After activity: 3 / 5

Why recommended?
• System Design ниже требования Senior: 2 / 4
• Активность даёт фактический рост +1
• Разрыв сокращается с 2 до 1
```

### 1.4. Activity Details

Показать title, description, type, duration (если есть в датасете), skills,
gain, max_level, причину рекомендации и ожидаемый результат.
Кнопка `Mark as Completed` входит в основной сценарий. `Start Activity` добавляется
после согласования серверного перехода статуса; не показывать неработающее действие.

### 1.5. Completion Flow

После подтверждённого ответа backend показать изменения и запросить новые рекомендации.
Блокировать повторное нажатие во время запроса; при ошибке не показывать успешное завершение.

```text

Career readiness: 68% → 76% (иллюстративные значения)
```

### 1.6. Activity History

Показать активности и статусы. Текущие внутренние статусы:
`completed`, `missed`, `registered`, `declined`.
Если в датасете встречается `skipped`, его значение и отображение согласовать отдельно;
не считать автоматически синонимом `missed`.

```text

System Design Basics  Completed
Public Speaking       Missed
Leadership Meetup     Declined
```

### 1.7. HR Dashboard

Базовый экран: количество сотрудников, средняя readiness, сотрудники без рекомендаций,
сводка gaps и завершений активностей. KPI «активные сотрудники» добавлять только после
определения периода и критерия активности. В UI отображать значения backend.

### 1.8. Skill Gaps

Показать число участников и статусы `completed`, `missed`, `declined`, `registered`.

Расширенные графики — P1.

### 1.10. Employees List

Таблица employee ID/имя, роль, грейд, readiness. Поиск и фильтры по роли/грейду — P1.

### 1.12. Dataset Import

HR-страница загрузки с результатом импорта и понятными ошибками валидации.

## 2. Backend Developer

### Стек и ответственность

Python, FastAPI, PostgreSQL, SQLAlchemy, Pydantic, Alembic, Pytest.
Backend владеет хранением, импортом, HTTP-контрактами, авторизацией и транзакциями.
Вызывает единые функции AI Engineer для gaps/readiness/scoring/симуляции;
не создаёт параллельную реализацию этих вычислений. Координирует сквозную интеграцию.

### 2.1. Database

Спроектировать модели и Alembic-миграции после изучения данных. Предварительные сущности:

| Сущность | Основные поля / назначение |
| --- | --- |
| employees | id, role, grade, tenure_months |
| skills | справочник навыков |
| employee_skills | employee_id, skill_id, level |
| grade_requirements | role, grade, skill_id, required_level; importance при наличии согласованного источника |
| events | id, title, type, description, ограничения по ролям/грейдам |
| event_skills | event_id, skill_id, gain, max_level |
| activity_history | employee_id, event_id, status, date и идентификатор участия |
| recommendations | сохранение/кэш результатов, если потребуется сценарию |

Переход к следующему грейду должен быть выражен в данных. Политику отсутствующих навыков,
повторного импорта и повторных участий согласовать по датасету до реализации.

### 2.2. Demo-доступ

Реализовать JWT и серверные роли `employee` / `hr`. Сотрудник получает доступ
к своему профилю и действиям; HR — к разрешённым профилям, аналитике и импорту.
Проверять роль и принадлежность данных в каждом бизнес-endpoint. Выбор роли в UI
не даёт полномочий. Секреты JWT/OpenAI остаются на backend.

### 2.3. Планируемый API

Все бизнес-endpoint'ы ниже — предложения для реализации, а не текущие маршруты.
Сохраняем префикс `/api/v1`; отдельно согласуем Pydantic-схемы запросов, ответов и ошибок.

| Метод и путь | Назначение |
| --- | --- |
| `GET /api/v1/employees/{employee_id}` | Профиль |
| `GET /api/v1/employees/{employee_id}/skills` | Навыки |
| `GET /api/v1/employees/{employee_id}/trajectory` | Текущий/следующий грейд, требования, gaps, readiness |
| `POST /api/v1/employees/{employee_id}/recommendations` | Рассчитать и вернуть до 3 рекомендаций |
| `GET /api/v1/events` | Доступные активности |
| `GET /api/v1/events/{event_id}` | Детали активности |
| `GET /api/v1/employees/{employee_id}/activities` | История участий |
| `POST /api/v1/employees/{employee_id}/activities/{event_id}/complete` | Завершение и результат изменения навыков |
| `GET /api/v1/hr/dashboard` | Базовые KPI |
| `GET /api/v1/hr/skill-gaps` | Сводка gaps |
| `GET /api/v1/hr/employees` | Список сотрудников |
| `GET /api/v1/hr/activity-stats` | Статистика активностей |
| `GET /api/v1/hr/recommendation-coverage` | Покрытие рекомендациями |
| `POST /api/v1/datasets/import` | Импорт с Pydantic-валидацией |

Текущий Next.js-прокси обслуживает только health/readiness. Backend и Frontend
должны расширить его для бизнес-маршрутов и передачи авторизации при интеграции.

### 2.4. Recommendations Flow

Загрузить профиль, требования, историю и доступные мероприятия. Вызвать функции
анализа gaps и ранжирования AI Engineer. Получить до 3 выбранных рекомендаций,
запросить объяснения и объединить их с исходными фактами. Отсутствие подходящих
мероприятий — допустимый результат; не дополнять список вымышленными активностями.

### 2.5. Complete Activity

В одной транзакции проверить доступ и состояние участия, зафиксировать завершение,
применить эффекты через существующую доменную функцию, сохранить навыки
и инвалидировать сохранённые рекомендации, если они есть. Рассчитать новую readiness
общей функцией и вернуть изменения. Повторный запрос для того же завершения
не должен повторно начислять gain, включая одновременные запросы.

Правило для каждого навыка, уже реализованное в `apply_skill_effects`:

```python
new_level = max(
    current_level,
    min(current_level + gain, max_level, 5),
)
```

Активность не уменьшает достигнутый уровень. Неизвестные навыки и дубли эффектов
не игнорируются; их нужно валидировать. Идентичность участия и возможность повторного
прохождения уточняются по датасету до фиксации контракта completion.

### 2.6. Dataset Import

Валидировать поля, ссылки между сущностями, уровни и статусы через Pydantic.
Показать результат или диагностируемые ошибки. Имена файлов выше — пример;
источник требований грейдов также определить по реальному набору данных.
Не хардкодить ID сотрудников: проверочные профили жюри должны работать без изменения кода.

### Проверки Backend

Pytest для импорта, доступа employee/hr, отсутствующих записей, completion и аналитики.
Проверить транзакционность, повторное/конкурентное завершение и отсутствие двойного gain.
Согласовать определения HR-метрик, протестировать их на известных данных.
Проверить миграции и полный demo flow совместно с остальными участниками.

## 3. AI Engineer

### Основная задача и границы

Построить детерминированный recommendation engine на чистом Python и адаптер объяснений.
OpenAI не выбирает и не переставляет активности. Scoring не зависит от сети и LLM.
Использовать текущие порты `RecommendationEngine.rank` и `ExplanationProvider.explain`;
нужные изменения контрактов согласовывать с Backend.

```text
Employee + requirements + history + events
    ↓
Skill Gap Analysis
    ↓
Candidate Generation
    ↓
Deterministic Scoring
    ↓
Top 1–3 + проверяемые факты
    ↓
OpenAI explanations / шаблонный fallback
```

### 3.1. Skill Gap Engine

Определить следующий грейд из данных и сравнить требования с текущими навыками:

```text
System Design: current = 2, required = 4
gap = max(required_level - current_level, 0) = 2
```

Согласовать обработку последнего грейда, отсутствующих требований и неизвестных навыков.
Не подставлять ноль вместо отсутствующего навыка без подтверждённого правила датасета.

### 3.2. Candidate Generation

Оставить мероприятия, подходящие роли, грейду и условиям доступности сотрудника,
дающие положительный фактический рост по нужным навыкам с учётом max_level.
Учитывать историю и согласованные правила повторного прохождения.

### 3.3. Scoring Engine

Пример факторов и весов — гипотеза для согласования, не утверждённая формула:

```text
score = skill_gap_impact * 0.40
      + grade_relevance * 0.25
      + participation_fit * 0.15
      + trajectory_impact * 0.10
      + diversity * 0.10
```

| Фактор | Смысл |
| --- | --- |
| Skill Gap Impact | Насколько фактический gain закрывает дефицит |
| Grade Relevance | Значимость навыка для следующего грейда |
| Participation Fit | Подтверждённые сигналы истории участия |
| Trajectory Impact | Изменение readiness после активности |
| Diversity | Разнообразие типов предлагаемых активностей |

До реализации зафиксировать нормализацию факторов, веса и устойчивое разрешение
равных баллов. Одинаковые входные данные должны давать одинаковый порядок.
Не трактовать пропуски как доказательство отсутствия интереса. Например, несколько
`missed` могут дать ограниченный штраф по согласованному правилу, но не должны
автоматически исключать важную активность. Не выдумывать историю при её отсутствии.

### 3.4. Impact Simulator

Использовать существующую `apply_skill_effects`, общую с completion backend.
LLM здесь не участвует. Правило для отдельного навыка:

```python
after = max(before, min(before + gain, max_level, 5))
```

Например: before = 2, gain = 1, max_level = 4 → after = 3.
Если before = 4, а max_level = 3, уровень остаётся 4. Фактический gain —
`after - before`; он может отличаться от заявленного gain мероприятия.

### 3.5. Career Readiness

Разработать одну понятную детерминированную функцию готовности к следующему грейду.
Согласовать веса требований, округление и обработку отсутствующих/нулевых требований,
последнего грейда и неполных данных. Backend и UI используют её результат.

Проценты `68%` и `76%` в этом документе — иллюстрации интерфейса, а не эталонные
ответы для приведённых навыков. После утверждения формулы заменить примеры
на согласованные входы и проверенные результаты.

### 3.6. LLM Layer — только объяснения

OpenAI получает уже выбранные Python engine рекомендации, факты и язык.
Не передавать личность сотрудника, если она не нужна для объяснения.
Использовать языковые коды `ru`, `kk`, `en` (KZ в продуктовых обозначениях — `kk` в API).

Пример смыслового содержания запроса; сериализацию согласовать с Backend:

```json
{
  "locale": "ru",
  "recommendations": [
    {
      "event_id": "EV014",
      "target_grade": "Senior",
      "skill_gaps": {"SK_SYSTEM_DESIGN": 2},
      "expected_gains": {"SK_SYSTEM_DESIGN": 1},
      "reason_codes": ["closes_target_grade_gap", "positive_skill_gain"]
    }
  ]
}
```

Ответ — структурированное отображение `event_id → текст`, например:

```json
{
  "EV014": "Активность повышает System Design на 1 уровень и сокращает разрыв до Senior с 2 до 1."
}
```

LLM не создаёт events, не меняет навыки, gain, требования, score, приоритеты и состав
рекомендаций. Проверить идентификаторы и соответствие ответа фактам; backend
присоединяет текст к исходным результатам Python engine.

### 3.7. Explainability

Объяснение должно содержать конкретные подтверждённые основания: текущий дефицит,
требование грейда, фактический рост, сокращение gap или релевантную историю.
Стремиться к трём факторам, когда данные их подтверждают; не выдумывать третий фактор.
Не использовать пустое «подходит вашему профилю». Числа должны совпадать с расчётом.

### 3.8. Fallback

При timeout, API error, rate limit или невалидном ответе сохранить исходные
рекомендации и порядок; вернуть шаблонные объяснения из тех же фактов.

```text
selected = deterministic_top_1_to_3
explanations = OpenAI(selected facts)
при ошибке объяснений → templates(selected facts)
result = исходный selected + explanations
```

Ошибка LLM не должна скрывать ошибки самого engine. Основной сценарий работает
без ключа OpenAI и при недоступности провайдера.

### 3.9. HR AI Insights — P1

Если останется время, сформировать подтверждённые данными выводы:

```text
Cloud Architecture
18 сотрудников имеют критический gap.
Подходящих активностей: 0.
Предложение HR: создать workshop по Cloud Architecture.
```

Порог «критического» gap согласовать заранее. Предложение создать мероприятие
не должно превращаться в вымышленную существующую активность.

### Проверки AI Engineer

Pytest для gaps, фактического gain, readiness, фильтрации кандидатов, устойчивого
порядка при равных баллах и отсутствия кандидатов. Проверить объяснения на соответствие
фактам, допустимые IDs, языки и fallback при сбоях. Использовать имеющиеся тесты роста
навыков; не создавать вторую реализацию ради симулятора.

## 4. Общие контракты команды

Перед параллельной разработкой согласовать минимальные JSON-примеры для профиля,
траектории, рекомендаций, completion, импорта и HR-метрик. Backend оформляет
Pydantic/OpenAPI-контракты; Frontend проверяет достаточность для экранов;
AI Engineer — соответствие вычисляемых полей доменным результатам.

Пример **будущего агрегированного HTTP-ответа**, а не текущего ответа LLM
и не существующей dataclass-модели:

```json
{
  "event_id": "EV014",
  "title": "System Design Workshop",
  "priority": 1,
  "score": 0.87,
  "skills": [
    {
      "skill_id": "SK_SYSTEM_DESIGN",
      "current_level": 2,
      "required_level": 4,
      "gain": 1,
      "predicted_level": 3
    }
  ],
  "career_readiness_before": 68,
  "career_readiness_after": 76,
  "reason": "Активность повысит System Design с 2 до 3 при требовании Senior 4."
}
```

Числа readiness и score иллюстративны. `priority` определяется Python engine,
`gain` — эффектом мероприятия, `predicted_level` — общей функцией симуляции.
Итоговые схемы и ошибки фиксируются совместно до подключения экранов.

| Frontend | Demo-вход, профиль сотрудника, траектория, карточки рекомендаций, completion flow, базовый HR-экран и загрузка датасета |

Для трёх человек сначала собрать сквозной сценарий на согласованных данных.
Backend координирует интеграцию; каждый участник отвечает за проверки своего компонента.
Серверные контракты объяснений предусматривают `ru`/`kk`/`en`; русскоязычный интерфейс
достаточен для первого demo, если ТЗ не требует иного.

### P1 — после работающего основного сценария

- Расширенные графики и Recharts, поиск и HR-фильтры.
- Развёрнутая история, дополнительные страницы HR и история рекомендаций.
- AI HR Insights.
- Полная локализация интерфейса RU/KZ/EN, если она не обязательна по ТЗ.
- Отдельный flow начала/регистрации активности после согласования статусов.

### P2 — после основного MVP

Points, badges, achievements, rewards, peer recognition, challenges и другая геймификация.

## 6. Главный Demo Flow

```text
1. Вошли как HR и загрузили dataset
        ↓
2. Открыли сотрудника с разрешённым доступом
        ↓
3. Показали текущий грейд и навыки
        ↓
4. Показали target grade и skill gaps
        ↓
5. Python engine предложил 1–3 активности
        ↓
6. Открыли «Почему?»
        ↓
7. Показали объяснение OpenAI или шаблонный fallback
        ↓
8. Mark as Completed в сессии сотрудника
        ↓
9. Навык изменился
        ↓
10. Readiness пересчиталась
        ↓
11. Рекомендации пересчитались
        ↓
12. Открыли HR Dashboard в сессии HR
        ↓
13. Показали общие skill gaps и статистику активностей
```

Для демонстрации выбрать из загруженного датасета профиль и активность с положительным
фактическим ростом. Прогнать сценарий без OpenAI и повторить completion:
объяснение остаётся доступным, повторного начисления навыка нет.

## Главный принцип

**Frontend:** понятно показывает решение и изменения состояния.

**Backend:** хранит данные, проверяет доступ, обеспечивает транзакции и связывает компоненты.

**AI Engineer:** детерминированно определяет полезный следующий шаг и формирует
подтверждённые фактами объяснения; OpenAI помогает только с их формулировкой.
