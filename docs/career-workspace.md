# Career Quest: employee and HR workspace

The employee screens live at `/`, `/career`, `/recommendations`, `/activities`, and
`/history`. HR uses `/hr`, `/hr/employees`, `/hr/skill-gaps`, `/hr/activities`, and
`/hr/import`. Sidebar navigation follows the authenticated role; HR can inspect an
employee's overview, trajectory, skills, recommendations, and history without
completing activities on their behalf.

The dashboard presents identity, role, tenure, current and target grade, readiness,
the most relevant skill gaps, and the first recommendation. Recommendation cards
show the explanation immediately, including the current level, target requirement,
expected gain, and available participation-history facts. A fallback explanation is
labelled as based on profile facts; it is not presented as generated by an LLM.

Skill requirements use **current / required**, with a completion checkmark. Full
skill lists without a grade requirement show the proficiency scale maximum of 5.
The grade order and requirements come from the API.

## Calculations and integration

`app/application/career.py` adapts persisted employee levels, grade requirements,
events, and participation history to the existing `DeterministicRecommendationEngine`
and `career_readiness`. It never replays imported gains over materialized levels.
The dataset's `as_of_date` is the business date for recommendations and HR metrics.

`app/api/career.py` supplies the trajectory, recommendations and HR analytics.
Existing catalog, completion, and import routers retain ownership of their routes.
There are no duplicate route registrations.

- `GET employees/{id}/trajectory`: current/target grade, ordered grades, readiness,
  skill requirements, current levels and critical-skill flags.
- `POST employees/{id}/recommendations`, `{language: "ru"}`: up to three ranked
  activities, predicted skills/readiness and grounded explanations from the existing
  explanation provider (with deterministic fallback).
- `GET events/{id}?employee_id={id}`: existing catalog details plus a personalized
  `preview` with current/predicted levels and readiness. Employee scope is checked.
- `GET hr/employees?include_readiness=true`: full directory with calculated progress;
  the original query without this option retains its existing read contract.
- `GET hr/dashboard`, `hr/skill-gaps`, `hr/activity-stats`,
  `hr/recommendation-coverage`: real aggregates of the loaded dataset.

HR's **active this month** counts distinct employees whose `in_progress` or
`completed` participation date falls in the snapshot's calendar month through the
snapshot date. Runtime completions use `completed_on`. Activity performance divides
status counts by all participation records for the event. Skipped groups `dropped`
and `no_show`; the remaining statuses are displayed separately, so percentages do
not silently exclude them. Unique participant counts are distinct from records.

## Completion and history

The UI uses the existing completion contract and sends a stable `Idempotency-Key`
on retries. Repeatable events require a participation or listed session date;
mandatory events require an assignment. The dialog explicitly labels completion
as a demo simulation because the backend permits future sessions.

The HTTP completion handler requests readiness calculation **inside the existing
completion transaction**. The response shows actual skill changes and readiness
before/after. On success the UI reloads profile, trajectory, skills, history,
recommendations and the activity catalog. Failures keep the dialog open and offer a
retry; they do not optimistically grant skills. Already-completed results are labelled.

History fetches all API pages before applying filters, so counts and filters cover
the entire history. The table paginates the filtered list in groups of ten. Original
statuses remain visible even when grouped under Skipped.

## Import

The four-file initial import and two-file append import use the existing multipart
endpoint. File selection, names, size and JSON syntax are checked before upload;
the backend validates references and saves atomically. Successful import reports
actual employee, event, skill and history counts. Append imports have fingerprint
receipts, so repeating a batch preserves subsequent runtime progress.

## Verification

Run `npm run typecheck`, `npm run build -- --webpack`, and `npm test` in `apps/web`.
Run `.venv/bin/python -m pytest apps/api/tests -q` from the repository root.
`test_career_api.py` covers the real database flow through recommendation,
completion, updated levels/readiness, changed recommendations, repeated completion,
HR permissions, initial import, and jury-profile append. PostgreSQL concurrency
checks additionally require `TEST_DATABASE_URL`.

The UI handles loading, errors with retries, empty results, final grades, and
mobile layouts. Browser-based visual verification requires an available browser
connection; API integration tests do not substitute for that visual check.
