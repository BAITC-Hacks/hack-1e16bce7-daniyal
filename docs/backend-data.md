# Backend: первый этап — данные

Реализованы задача 2.1 и CLI-часть задачи 2.6 из `team-tasks.md`.
HTTP-endpoint импорта и append новых профилей теперь реализованы: [backend-workflows](backend-workflows.md).

## Соответствие датасету

- `skills`, `role_grades`, `grade_requirements`: справочник, следующий грейд,
  требования и признак critical. Порядок Junior → Middle → Senior → Lead взят
  из README датасета и сохранён в БД для каждой роли; у Lead следующий грейд null.
- `employees`, `employee_skills`: профиль, карьерная цель, язык, руководитель,
  даты найма/оценки; исходный `assessed_level` и восстановленный текущий `level`.
- `events`, `event_skills`, `event_prerequisites`: аудитория, формат, даты сессий,
  обязательность, эффекты и prerequisites. Массивы аудитории и дат хранятся в JSON.
- `activity_history`: идентичность участия — исходный `record_id`; статусы
  сохраняются без преобразования: completed, in_progress, dropped, no_show,
  declined, overdue. Сохраняются оценки, дедлайн, инициатор и completion_pct.
- `dataset_state`: дата среза, метаданные, шкала и SHA-256 валидированного набора.

Дата среза берётся из `meta.as_of_date` (в комплекте 2026-10-01), не из часов сервера.
Неизвестные ID навыков отклоняются; отсутствующий известный навык сотрудника = 0.
Для каждого сотрудника сохраняются все навыки каталога, без хардкода employee ID.

Завершения строго после `last_review_date` применяются через общую доменную функцию
`apply_skill_effects` в порядке `(date, record_id)`. Завершения до этой даты и в саму
дату уже считаются включёнными в оценку. Исходный assessed_level сохраняется.
`effects_applied=true` у всех импортированных completed означает, что результат
уже учтён — исходной оценкой либо восстановлением истории. Другие статусы gain не дают.

Повторяемость сохраняется в `events.repeatable`: только EV_036 согласно README
датасета. Исторические участия сохраняются по record_id без дедупликации по event_id.
Сервис нового завершения должен отдельно проверять повторяемость и блокировать
двойное начисление; CLI-импорт такой HTTP-сценарий пока не реализует.

## Импорт

Команды из `apps/api`:

```sh
../../.venv/bin/alembic upgrade head
../../.venv/bin/python -m app.import_dataset ../../dataset --validate-only
../../.venv/bin/python -m app.import_dataset ../../dataset
```

Pydantic проверяет схему, диапазоны, уникальность ID, связи, карьерные цели,
руководителей, согласованность статуса и процента завершения. CSV-ошибки содержат
номер строки. При ошибке БД CLI не выводит строку подключения.

Первичная загрузка выполняется одной транзакцией. Повтор такого же валидированного
содержимого возвращает `unchanged`, даже если прогресс в БД впоследствии изменится.
Массивы входят в fingerprint с исходным порядком: перестановка записей считается
изменением снимка. Другой набор отклоняется без удаления или перезаписи данных.
Параллельные импорты сериализуются PostgreSQL advisory lock.

Добавочный HTTP-импорт новых проверочных профилей и их истории реализован.
Изменение существующих профилей и замена полного снимка по-прежнему не поддерживаются;
альтернативный полный набор можно загрузить только в пустую БД.

## Проверка

Обычный pytest проверяет реальный комплект, восстановление навыков, границу даты
оценки, валидацию, откат ошибки и идемпотентность на SQLite с включёнными FK.
Дополнительный тест на PostgreSQL создаёт временную схему и удаляет только её:

```sh
TEST_DATABASE_URL='postgresql+psycopg://career_quest:career_quest_dev@127.0.0.1:55432/career_quest' \
  .venv/bin/python -m pytest -c apps/api/pytest.ini apps/api/tests -q
```

Команда выполняется из корня. Проверяет upgrade/downgrade/upgrade, `alembic check`
и два конкурентных импорта. Основные таблицы приложения не затрагиваются.
